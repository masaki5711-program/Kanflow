# GitStation のチェック `kanflow/acceptance`（受入の準備の報告）

2026-11-10。Kanflow が、PBI にひも付いた開いているマージリクエスト（MR）ごとに「受入の準備ができているか」を
GitStation のチェックとして報告する。相手の仕様は GitStation の `docs/api/checks.md`（Checks API）。

**報告するだけ**で、マージを止めるかどうかは GitStation 側の設定（保護ブランチの必須チェック）が決める。
最初は 1 つのプロジェクトで、必須にせずに様子を見る。

## 使い始めるまで

1. **GitStation の管理者**が、Kanflow の連携のサービスアカウントに、対象のプロジェクトで名前空間 `kanflow` の
   チェックを報告する許可を出す。
   `gstn admin service-account grant-checks <id> --project <p> kanflow`
   （API: `PUT /api/v1/admin/service-accounts/{id}/check-grants/{project_id}/kanflow`）
2. そのサービスアカウントが、対象のプロジェクトで **Developer 以上**であること。
3. **Kanflow** のプロジェクト設定 → Git 連携で「受入の準備を GitStation に報告」を入にする
   （PO / SM / 管理者。取り込み元が GitStation のときだけ出る。初期値は切）。

1・2 が無いと、GitStation は報告を拒否する（403、`FG-AUTH-0003`）。Kanflow は Git 連携の設定にその旨を出す
（下の「うまくいかないとき」）。

## 何を見て判定するか

MR にひも付いた PBI（削除されたものを除く）の**すべて**が、次の 2 つを満たせば `success`、足りなければ
`action_required`。

| 条件 | 中身 |
|---|---|
| 開いているスプリントにタスクがある | 状態が 計画中 / 実施中 / レビュー のスプリントに、その PBI のタスクが 1 つ以上 |
| 受入基準ごとに確認の方法が決まっている | 受入基準が 1 つ以上あり、そのすべてに確認の方法（試験 / 検査 / 測定 / 承認）が入っている |

- ひも付いた PBI がすべて削除されているときは `action_required`（ひも付けを確認してもらう）。
- 「作業の主張がぶつかっている」という条件は、この版では見ない。
- 報告の本文（`summary`）は日本語の平文で、**PBI の番号だけ**を書く（`PBI-12`）。題名・受入基準の文・人の名前は
  書かない。番号は 1 行に 20 件までで、残りは「ほか N 件」。`details_url` は付けない。

## チェックが付かない MR

次の MR には、Kanflow は**何も報告しない**（チェック自体が無い）。

| MR | 理由 |
|---|---|
| PBI にひも付いていない | 判定するものが無い |
| 機密の PBI にひも付いている（ほかの PBI と一緒でも、その PBI が削除済みでも） | D-5。機密の PBI については、番号も「足りない」という事実も外に出さない |
| 読めない PBI にひも付いている（別のプロジェクトの PBI など） | 同上 |
| Kanflow のスイッチが切、または取り込み元が GitStation でない | 報告しない設定 |

機密かどうかは**報告のたびに**読む。判定のときと、GitStation へ送る直前の 2 回。報告のあとで PBI が機密になったら、
それ以降は報告せず、前の報告はそのまま残る（消すと「機密になった」ことが分かってしまうため、触らない）。
送る直前の確認と送信のあいだ（1 回の HTTP の時間）に機密になった場合だけは、その 1 件が届く。

したがって、**チェックが無いことからは理由が分からない**。GitStation でこのチェックを必須にすると、上の MR は
「報告なし = 満たしていない」としてマージできなくなる（GitStation は報告が無いことを成功と見なさない）。
必須にする前に、PBI にひも付かない MR と機密の PBI の MR をどう通すかを決めること。

### 知っておくこと（決めていない点を含む）

- **機密でない PBI の準備の状態は、GitStation でその MR を見られる人の全員に見える**（PBI の番号と、足りているか
  どうか）。Kanflow でそのプロジェクトを見られない人も含む。
- **前の報告は取り下げない。** PBI が機密になったあとも、機密になる前に書いたチェック（番号を含む）は GitStation に
  180 日残る。
- **チェックが途中から更新されなくなった MR** は、「機密の PBI がひも付いた」可能性を示す（PBI にひも付かない MR
  には最初からチェックが無いので、区別がつく場合がある）。これを避ける案は「機密の PBI をひも付いていないものとして
  扱い、残りの PBI だけで判定する」こと。その場合、機密の PBI だけの MR はチェック無し、ほかの PBI もある MR は
  チェックが付き続ける。どちらにするかは**未決**（いまは「何も報告しない」）。

## いつ報告するか

Git の同期（既定で 180 秒ごと）のたび、GitStation のイベントの取り込みのあとに 1 回動く。

- チェックは MR の**いまの先頭のコミット**に書く（GitStation は先頭のコミットのチェックだけを数える）。
  書く前に必ず GitStation から MR を読み、そのときの先頭のコミットに書く（覚えているコミットには書かない）。
- 同じコミットに同じ判定なら、もう送らない。判定が変わったら書き直す（同じコミットなら GitStation は上書きする）。
- 判定が変わっていないとき、先頭のコミットは、MR のひも付けが変わったとき（同期が MR の更新を見たとき）と、
  最後に読んでから 30 分たったときに読み直す。push がひも付けに現れなかった場合、新しいコミットにチェックが
  付くまで最大で 30 分ほどかかる。
- 1 回に GitStation へ問い合わせる MR は、全プロジェクトを合わせて 30 件まで。**リポジトリごとに 1 件ずつ順番に**
  取り（長く待っているリポジトリから、その中では長く待っている MR から）、残りは次の回に回す。MR の多い
  リポジトリや失敗しているリポジトリが、ほかのリポジトリの分を使い切ることはない。
- 送る前に、リポジトリが GitStation でこの Kanflow のプロジェクトにだけ結び付いていることを確かめる。
  ほかのプロジェクトに結び付いたリポジトリには書かない（設定に理由を出す。下の表）。
- GitStation で MR が閉じられていたら（イベントがまだ届いていなくても）報告しない。
- ひも付けが「開いている」でなくなった MR は、Kanflow の記録から外す。

## うまくいかないとき

失敗は同期を止めない。MR の行に記録して、Git 連携の設定のスイッチの下に、いちばん新しいもの 1 件を出す。
記録する文は日本語で、画面では見る人の言語（ja / en / id）で出る。次に成功するか、送るものが無くなると消える。

失敗には 2 つの種類がある。

- **その MR だけの失敗**（報告先のコミットが無い、など）: ほかの MR は続ける。
- **リポジトリ全体の失敗**（拒否された、GitStation が使えない・届かない、トークンを拒否された、結び付いていない）:
  どの MR で試しても同じなので、その回はそのリポジトリの残りを送らず、待ち時間が過ぎるまでそのリポジトリの
  MR を 1 件も試さない。ほかのリポジトリは続ける。

| 起きたこと | 表示 | 種類 | やり直し |
|---|---|---|---|
| 報告を拒否された（403、`FG-AUTH-0003`） | 管理者に許可（check-grants）と Developer 以上を依頼する旨 | リポジトリ全体 | 1 時間後 |
| 報告先のコミットが無い（404、`FG-REPO-0023`） | コミットが見つからなかった旨 | その MR だけ | 次の回に先頭のコミットを読み直して送る。続けて失敗すると下の間隔 |
| 利用制限に達した（429） | 利用制限に達した旨 | リポジトリ全体 | 次の回。続けて失敗すると下の間隔 |
| GitStation が一時的に使えない（503）・届かない | 一時的に利用できない / 接続できなかった旨 | リポジトリ全体 | 同上 |
| トークンを拒否された（401）・読む権限が無い（403）・ホストが許可されていない | それぞれの旨（リポジトリの同期のエラーと同じ文） | リポジトリ全体 | 1 時間後 |
| リポジトリが GitStation に見つからない・このプロジェクトだけに結び付いていない・連携 ID が無い | その旨 | リポジトリ全体 | 1 時間後 |
| MR が GitStation に見つからない（読み取りの 404） | 見つからない旨 | その MR だけ | 1 時間後 |
| そのほかの応答（500 など、想定外の形の応答） | エラーを返した旨（状態コード付き）/ 想定外の応答の旨 | その MR だけ | 次の回。続けて失敗すると下の間隔 |
| トークンが保存されていない・復号できない | 出さない（ログだけ。同期の側のエラーとして出る） | — | 次の回 |

やり直しの間隔（続けて失敗した回数で決まる）: 1 回目は次の回、そのあとは 10 分、20 分、40 分、以後 1 時間。
直せば解ける種類の失敗（拒否・権限・結び付き）は最初から 1 時間。成功すると回数は 0 に戻る。
**トークンか連携 ID を入れ替えると、待たずに次の回でやり直す**（プロジェクトの設定のトークン・連携 ID は
プロジェクトの全リポジトリ、リポジトリごとのトークンはそのリポジトリ）。同じ連携 ID を送り直しただけでは変わらない。
**スイッチを切にして入れ直しても、待たずにすぐやり直す**（管理者が許可を出した直後など。こちらは記録も消えるので、
開いている MR のすべてに報告し直す）。

報告の送信そのものは 1 回だけで、同じ回の中では繰り返さない（読み取りは 429 / 503 のとき 2 回までやり直す）。

サーバーのログ: `acceptance check not reported`（MR ごとの失敗）、`acceptance check skipped: repository not readable`
（つながらない・結び付いていない）、`acceptance check skipped: no readable token`（リポジトリごとに 1 回の回で 1 行）、
`acceptance check failed`（GitStation の応答ではない失敗。どの段階か `stage` = `read` / `report` / `internal` と、
元のエラーが付く。記録せず次の回にやり直す）、`acceptance check reported but not recorded`（GitStation には届いたが、
Kanflow の記録を書けなかった。次の回にもう一度送り、GitStation が同じチェックを上書きする）、
`acceptance check planning failed`、`acceptance check failure not stored`（記録できなかった失敗の文も付く）、
`acceptance checks reported`（件数）、`acceptance check tick failed`（1 回まるごとの失敗）。

## 切にしたとき

- Kanflow は「何を報告したか」の記録（失敗の記録も）を消す。スイッチを切にしたときだけでなく、取り込み元を
  GitStation 以外に変えたとき、Git 連携を無効にしたときも同じ。**GitStation に書いたチェックは取り下げない**
  （GitStation が 180 日で消す）。古い判定が残るので、必須にしているなら GitStation の設定も見直すこと。
- 報告の途中で切にした場合、すでに送信中の 1 件は届くことがある。それより後は送らず、記録も作り直さない。
- もう一度入にすると、開いている MR のすべてに報告し直す。
- 切り替えは活動の履歴に残る（`git.stationAcceptanceCheck`）。

## この版の制限

- GitStation に書く本文は日本語だけ（GitStation の画面を見る人の言語に合わせない）。Kanflow の設定に出す失敗の文は
  ja / en / id。
- Kanflow の画面へのリンク（`details_url`）は付けない。
- 設定に出す失敗は、プロジェクトでいちばん新しい 1 件だけ（どのリポジトリ・どの MR かは出さない。ログにある）。
- リポジトリ全体の失敗は、それに当たった MR の行に記録する。その MR が次に成功するか、開いている MR で
  なくなるまで、設定に残ることがある。その MR について送るものがなくなっても（判定が元に戻った、機密の PBI に
  ひも付いた）、待ち時間が過ぎるまでは行に残し、リポジトリのほかの MR も待たせる。その MR が閉じると行ごと消えるので、
  待ち時間はそこで終わる（ほかの MR は次の回に試す）。
- 実際の GitStation での確認は、上の「使い始めるまで」の 1・2 が済んでから。それまでは、GitStation の仕様どおりに
  振る舞う試験用の相手（`fake-gitstation.ts`）と実際の PostgreSQL での試験まで。
